"@runfusion/fusion": patch
---

summary: Executor verification calls persist write-ahead, are watchdog-bounded, and reclaim stale records.
category: fix
dev: Executor-invoked `fn_run_verification` calls previously persisted nothing — only the chat-queue path wrote a `task_verification_requests` row — so `fn_task_verification_status` answered "No verification request exists" for tasks that had run dozens of executor verifications, and a killed run left no inspectable record. The tool's slot-queue wait (`withVerificationSlot`, effective limit 1) had no timeout and no AbortSignal, the subprocess promise was resolve-only, and a 60s synthetic-heartbeat loop kept refreshing stuck-detector activity — so a call whose child never emitted `close` wedged the executor run for 50+ minutes (observed live on 2026-08-31: EXAM-002 wedged ~5x, ~51 min and ~20+ min hangs), and the orphaned `running` row then blocked every follow-up verification on that task with "already in flight" until an operator restarted the agent. The fix has three parts. (1) Write-ahead persistence: every tool invocation persists a project-scoped record BEFORE slot acquisition or spawn via new `upsertExecutorVerificationRequest` (claims an unclaimed chat request in place preserving its requestId; never steals a live `running` row), and writes a terminal `passed`/`failed` record on every settle path, so `fn_task_verification_status` always returns the latest record — including stale/failed ones — for any task that issued calls. (2) End-to-end watchdog: the new `verificationWatchdogTimeoutMs` project setting (default 600000, clamped to the 1800s hard cap; 0 disables) bounds queue wait plus subprocess in one ceiling; on expiry the queued acquisition is aborted, the child is SIGTERM→SIGKILL escalated, the non-sandbox path now settles on abort (previously the signal was honored only while queued), and the result is an explicit `timedOut` failure with a persisted terminal record naming the ceiling. (3) Stale reclaim: `reclaimStaleTaskVerificationRequest` CAS-transitions a `running` row older than the ceiling to terminal `failed` (guarded by requestId + startedAt so a live executor is never stolen), and the executor's verification pickup loop reclaims stale rows before claiming, brackets itself with stuck-detector begin/end, and applies the same watchdog ceiling. Regression coverage proves failing-before/passing-after: kill-mid-verification acceptance tests assert record survival, explicit watchdog settlement within the ceiling, and a clean subsequent request; reverting the fix source reproduces the original defects (unbounded test timeouts, missing records).
