summary: Isolation-mode switches stop waiting on dead cards, and a refused switch now names what it waits on.
category: fix
dev: The busy guard behind `PATCH /api/projects/:id` asks the owning runtime before refusing: when the in-flight metric says busy it resolves the holding card ids and reads their board rows in one batched, lane-scoped store read, releasing a card only where its row is `status: "failed"` in the in-progress lane (the canonical terminal park) while a `failed` row in `todo`/`in-review`, a card the read did not describe, a rejected or timed-out read, or a runtime with no such path keeps the previous conservative refusal. Two code-owned budgets bound it — `ISOLATION_BLOCKER_READ_TIMEOUT_MS` (500 ms) per decision and `ISOLATION_BLOCKER_STORE_READ_TIMEOUT_MS` (300 ms) for the single read inside it — so a slow board can only restore the old answer, never a permissive or a late one. `force: true` never consults the board. The 409 body gains `details.blockingTaskIds` (omitted, never sent empty, when nothing could be named); `details.activeTaskCount` is unchanged. A proven-clear answer also carries the remaining `runtimeStopDrainMs` budget so the shutdown that follows is charged for the decision that unlocked it. The new optional `getInFlightBlockers()` runtime capability answers in-process from its own store and over IPC (`GET_IN_FLIGHT_BLOCKERS`) from an isolated child, which clamps to the inner budget; `remote-node` deliberately does not implement it, so a remote project keeps the historical refusal rather than trusting a cross-node answer.
