summary: A card that lands in the review lane now gets reviewer work promptly, however it got there.
category: feature
dev: STAS-205 — a card could reach the review lane with no committed record of how it got there, and a review verdict could reach a human with no attributable attempt behind it: `task_lifecycle_events` was CHECKed to `task:deleted` alone, so lane entry could not be recorded as a lifecycle event at all, and `task_reviewer_runs` had a schema and zero writers (0 rows DB-wide after 534 review-lane entries across 82 tasks), so the question "has reviewer work already begun for this card?" had no data behind it. The store's move transaction now appends `task:entered-review` with previous column, target column, entry timestamp and the `moveSource` that names the path; engine, scheduler, workflow-graph, completion-handoff, dashboard-drag and CLI-bundle entries all funnel through that one move implementation, so every entry path is covered by the same code rather than by call-site discipline. `lifecycle-outbox` replaces its single-literal event type with a discriminated union, so a new event type cannot borrow another type's payload. `reviewer-run-ledger` becomes the ledger's first writer (open/complete/invalidate/list) and is re-exported from the `@fusion/core` barrel; its open row is the idempotency key a restarted dispatch pass re-derives from committed state. `ReviewDispatchSweep` consumes that state every 15 s: it classifies each review-lane card into one named bucket, dispatches the ones with no live reviewer work through the heartbeat launcher (so the reviewer session starts in-process instead of waiting hours for that agent's own patrol), and bounds retries from committed ledger rows so a restart cannot hand a wedged card a fresh budget. Migration `0090_stas_205_review_lane_ledger.sql` widens `task_lifecycle_events_type_check` to include `task:entered-review` and adds the partial unique index `task_reviewer_runs_live_unique (project_id, task_id, reviewer_agent_id) WHERE invalidated_at IS NULL`, which makes a concurrent or re-run second dispatch a no-op instead of a duplicate reviewer session; prior attempts are invalidated rather than deleted, so rework history stays attributable. No backfill: historical entries had no such record written, and inventing lifecycle events would fabricate dispatch facts that never existed.
