summary: Board stops slowing down as cards pile up: History, board sweeps and search no longer read whole task rows.
category: performance
dev: Four defects, one symptom, shipped as one change (RUFU-304/309/310/311). (1) Task History appends move off the task row into append-only `project.task_log_entries` plus a per-card `task_log_rollup` and a backfill witness (migration 0093): a pure append now writes only the side table — no `tasks` write, no `updated_at` bump — while compound writers keep their own state write and send their entry to the same table. Reads merge the legacy `tasks.log` prefix with the side rows, and the derived stall/timing envelope may be authored by the row (stamped `tasks.log_projection_at`) or the rollup, newest stamp winning. (2) Board/list reads project only the columns the board renders instead of `SELECT *`. (3) Engine board sweeps (self-healing, scheduler) batch their workflow-selection reads — one `task_id = ANY(...)` query per page plus one IR read per distinct workflow, through a pass-scoped cache; a cache-less resolver call is caught by `sweep-selection-read-shape.test.ts`. (4) `project.tasks.search_vector` and its `archive.archived_tasks` mirror are rebuilt from title+description under the `simple` config (migration 0094), so comment writes stop re-deparsing the comment history into a stored-generated column and its GIN entries; comment text and task ids stay searchable through the literal ILIKE arm, and `GET /tasks/page?q=` now shares `buildTaskSearchPredicate` with `searchTasks`, so a query containing punctuation returns the same cards on both endpoints. Existing databases are backfilled and re-checked at boot; the search-vector rebuild rewrites each task table once. Heap-space reclaim (`VACUUM FULL`, `pg_repack`) and dropping the legacy `tasks.log` column stay operator-decided maintenance and are documented in `docs/storage.md` — never automated.
