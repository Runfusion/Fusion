summary: Post-merge Full Suite gate checks CI in the repo named by postMergeCiRepo and refuses honestly when it is unset.
category: feature
dev: New project-only setting `postMergeCiRepo` (an `owner/repo` slug validated by `validateGithubRepoSlug`) is resolved at gate-dispatch time in the engine and substituted into the built-in post-merge prompt's `{{ciRepo}}` token, so the reviewer searches the repository that actually runs CI instead of guessing from its checkout's `origin`. Unset or malformed values start no session: the gate records the new not-run reason `ci-repository-unresolved` (`status: "skipped"` plus `notRunReason`) with a refusal that names the setting key, separates the publishing remotes the project **declares** (`merge.pushRemote`) from the ones that merely **exist** in the checkout — a remote existing is not authorization to publish there — and states that no run was searched for; it never claims a run is absent. Projects whose built-in workflow carries the post-merge Full Suite gate (`gateMode: "gate"`, `defaultOn: true`) MUST set `postMergeCiRepo`, and the refusal stays recoverable rather than becoming a dead end: the not-run row is judged as evidence that never arrived, so **Retry** or the bounded automatic re-seed (three attempts) re-runs the gate once the setting is set, while a refusal an operator already waived with the audited bypass is honored and never re-run. The reason vocabulary gained one entry in `WORKFLOW_STEP_NOT_RUN_REASONS`, mirrored by hand in `packages/dashboard/app/utils/taskProgress.ts` (drift-tested), labeled in `WorkflowResultsTab` and the seven locale catalogs; the key ships with no Settings UI row yet, registered in the dashboard's not-surfaced allowlist.
