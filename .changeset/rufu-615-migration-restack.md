summary: Migrations are numbered so an upstream release can no longer make Fusion skip a schema change silently.
category: fix
dev: `fusion_schema_migrations.version` is a bare number and the skip test is `applied.includes(version)`, so a number may name exactly one migration per database. This line resolved every upstream collision by renumbering the INCOMING upstream file and keeping its own slots, so production databases recorded 0087/0088/0089 as the fork's migrations while the bundled files at those numbers were upstream's — and the files that own those slots were skipped there permanently, with no error anywhere. Restacked: upstream's released numbers are adopted verbatim (`0086_fn_9429_stale_review_callback_waiver_receipts.sql`, `0087_fn_9439_pull_request_readiness.sql`, `0088_fn_9512_recovery_disposition.sql`), this fork's own SQL moves to the tail (`0090_fn_332_overlap_owner_fk_repair.sql` was 0087, `0091_stas_205_review_lane_ledger.sql` was 0088, `0092_rufu_615_task_log_projections.sql` was 0091 under the previous numbering), and 0089 is left as a gap because upstream took it for FN-9529. PR readiness, recovery disposition and the task-log projections gained live-schema probes beside their marker check, so a database that recorded one of those slots under a different migration re-applies the idempotent DDL instead of skipping it forever. `migration-wiring-integrity.test.ts` now fails the merge gate when a recorded marker disagrees with its own filename or when one number names two migrations. Upgrading databases need no manual repair; a database that recorded 0089 for anything other than FN-9529 must have that row deleted before this fork ships 0089.
