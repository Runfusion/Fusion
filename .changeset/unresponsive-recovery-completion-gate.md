summary: Stop re-waking an agent for a heartbeat tick that already finished cleanly, and back off repeat recoveries.
category: fix
dev: STAS-308 — `unresponsive-recovery` asked only whether an in-memory tracked tick was still ticking, a question a hung client answers forever, so one stuck tick produced a fresh recovery wake every window (STAS-270 measured four in fourteen minutes, each an empty-inbox session burning a full agent session; STAS-264/281/227 repeat the class) even though every later tick closed cleanly with `fn_heartbeat_done`. Both halves of recovery now consult one bounded page of the agent's durable run history before spending a session: `recoverUnresponsiveAgent` at episode start, and `executeHeartbeat` at the queued wake's fire time — which matters because STAS-270 measured that recovery dispatches queue behind the per-agent start lock, so the evidence that justified the episode can be minutes stale by the time the wake runs. Proof of life is a run past the stuck tick that closed `status: "completed"` with a non-null `endedAt`; `terminated` and `failed` never qualify, because recovery writes `terminated` for the run it kills and would otherwise certify its own victim as proof the agent is alive. A cancelled episode still disposes and untracks the hung session but terminates no run, pauses nothing and dispatches no wake; a cancelled queued wake opens no run and releases the wake-goal claim it had reserved. Every cancellation is durable as `agent:unresponsive-recovery-cancelled` so recovery that skips itself is as auditable as recovery that fires. Recovery for an agent that genuinely never finishes a tick is unchanged, and each episode an agent takes now earns a doubling cooldown (twice the recovery window, capped at six hours, exposed as `getRecoveryBackoff`) instead of an identical wake every window.
