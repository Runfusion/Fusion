# Diagnostics

## Settings changes in the Activity Log

Changed project or global settings produce a `settings:updated` Activity Log entry, except engine-owned churn (`engineLastActiveAt`, `engineActiveSinceMs`, `postgresMigrationInboxMessageSentAt`, and `secretsSyncPassphraseConfigured`) and dashboard restore state (`dashboardCurrentProjectIdByNode`). The dashboard field remains live global state so a browser can restore its last project, but it is not operator configuration and therefore creates neither a settings activity row nor a configuration revision snapshot. Secret-bearing values are redacted or summarized. Workflow setting values, including `requirePrApproval`, never appear in this payload; use the configuration revision history for those changes. See [Who changed this setting, and when](#who-changed-this-setting-and-when-configuration-audit-trails) for both audit mechanisms and their query contracts.

## Who changed this setting, and when (configuration audit trails)

Fusion provides two complementary audit surfaces: append-only configuration revisions for project settings and the Activity Log for concise operational events. The related rebase controls are documented in [Worktree and pre-merge rebase settings](settings-reference.md#worktree-and-pre-merge-rebase-settings).

### Configuration revision history

`GET /api/config/revisions` reads project-setting revisions from the PostgreSQL async revision store. It accepts only `configKind=project-settings` (or an omitted `configKind`), returns newest first by `createdAt` and `sequence`, and supports `limit` (1–500; default 100) plus `offset`; the response includes `hasMore`. This route is unavailable without the PostgreSQL async layer.

`POST /api/config/revisions/:revisionId/rollback` applies a selected historical revision and records that action as a new, forward-only rollback revision rather than deleting history. The `configuration_revisions` table stores project-partitioned records including `changed_by`, `before`, `after`, `diffs`, `source` (`mutation` or `rollback`), and the database-assigned `sequence` that orders same-timestamp writes. `GLOBAL_CONFIGURATION_OWNER_ID` is the reserved owner for user-global settings history, preventing it from being attributed to whichever project happened to issue the write.

### Activity Log

`GET /api/activity` returns newest-first events. Its query parameters are `limit` (default 100, maximum 1000), `since` (an ISO timestamp), and `type`. Valid types are `task:created`, `task:moved`, `task:updated`, `task:deleted`, `task:merged`, `task:failed`, and `settings:updated`. `DELETE /api/activity` clears the activity log for maintenance. `settings:updated` entries are generated by the Task Store listener using the generic diff policy in `packages/core/src/task-store/settings-activity.ts`.

### Agent activity stream

`GET /api/agent-activity` is a separate project-scoped history for agent-attributed task, gate, approval, and state transitions; it does not expand the Activity Log type contract. Its inspectable wire, cursor, continuation, and retention contract is [Agent activity API contract](agent-activity-contract.md). Live dashboards receive durable `agent:activity` SSE frames; reconnecting consumers can close any bounded-tail truncation gap through this route. Payload metadata is IDs/counts/outcomes-only, and only roster-proven `agent` attribution represents an org-map node.

### Current behavior and limitations

- **Attribution:** revision `changedBy` records the actor supplied to the settings mutation. Older investigations may encounter historical `{ kind: "human", id: "local-user" }` records, but current settings-operation defaults use the system actor when a caller supplies none; treat historical attribution according to the stored record.
- **Revision history:** the API is paginated rather than capped to one unpageable 100-row window. Request later pages with `offset`; concurrent appends can make offset pages overlap, so preserve revision IDs when collecting an incident timeline.
- **Activity coverage:** the former allowlist is removed. All changed project/global settings are recorded except the churn, secret-configuration, and dashboard restore-state exclusions above; values for sensitive keys are redacted. Workflow settings remain outside the `settings:updated` payload.

## Debug-level diagnostics (`FUSION_DEBUG`)

Engine and core subsystem loggers (`createLogger`) expose a `debug()` level for routine diagnostics. It is **off by default** so the TUI log pane and engine stderr show state *changes* rather than repeated resting-state chatter.

| Severity | Use it for |
| --- | --- |
| `debug()` | Repeated poll/sweep lines with unchanged state, expected skips and no-ops, per-item progress, expected-and-handled failures (fallback/retry/optional dependency), and diagnostics already recorded as run-audit events. |
| `log()` | A state transition or operator-visible event. |
| `warn()` | Handled degradation that needs eventual operator attention. |
| `error()` | An unrecovered failure requiring operator action; do not use it when code recovered or scheduled a retry. |

Most new diagnostic sites should therefore start at `debug()` and only be promoted when they meet a higher-severity rule. `debug()` output is enabled per subsystem with the logger prefix:

```bash
FUSION_DEBUG=scheduler        # one subsystem
FUSION_DEBUG=scheduler,merger # several
FUSION_DEBUG=1                # everything (also: true, all, *)
```

The variable is re-read per call, so it can be toggled on a long-lived process without recreating loggers. Debug lines emit under the `info` severity marker and render like any other info line.

Currently debug-gated classes include local/default routing, capacity and re-entrancy skips, poll/sweep no-actions, per-step success/progress, optional integration probes, successful verification bookkeeping, per-session agent setup (`agent-session` runtime/fallback resolution, planning mode, stuck-detector track bookkeeping), per-skill selection chatter and intentional skill-exclusion notices (`[skills] info: … disabled by project execution settings`), expected-missing PROMPT.md seed reads (ENOENT), token-cache metrics JSON, duplicate runtime `Specifying …` echoes, zero-count recovery summaries, mission "no linked feature" skips, event-driven "triggering scheduling" echoes, auto-claim snapshot invalidation, assignment-trigger skip guards (ephemeral/disabled/active-run), runtime `Scheduled`/`Started executing` echoes of executor `Starting`, worktree warm-reuse, runtime-env injection counts, baseCommitSha capture, parse-steps reconcile diagnostics, graph node worktree re-acquire, ephemeral already-owned worker skip, embedded-postgres rejoin "already running", and `fn_run_verification` non-timeout command-fail detail (failed `done` lines stay at info). Each agent session instead emits one normal-level `[skills]` summary with the available count, resolved forced skills, and any unavailable forced requests. State-changing recovery and dispatch outcomes remain visible (`Starting`/`Specifying`/`Worktree created`/`Auto-merge merged`/column moves/slow hold-release).

Dashboard server code uses the core logger only: `import { createLogger } from "@fusion/core";`. Do not import an engine logger, use a relative cross-package logger path, or add a dashboard-local logger implementation.

`packages/engine/src/__tests__/log-severity-manifest.ts` and package contract tests pin individual demotions and the no-bare-console rule. This makes an accidental severity reversion a CI failure instead of an operator-visible log flood.

## Run-audit sink diagnostics (`GET /api/diagnostics/run-audit-sink`)

A best-effort audit row is accepted before it is durable, so "is telemetry being lost?" needs a number rather than a
log grep. `GET /api/diagnostics/run-audit-sink` answers it from the daemon's own memory: `available`, `buffered`,
`pid`, the sink writer's counters (`accepted`, `coalesced`, `written`, `batches`, `batchFailures`, `queueDepth`,
`queuePeak`, `timedOut`, `lateRecorded`, `slowWrites`, `maxLatencyMs`, `spilledToDeadLetter`,
`deadLetterSuppressed`), and the dead-letter file's `path`, `bytes`, `rows`, `suppressed`, and `writeFailures`.
Appending `?rows=1` additionally returns the file's tail with `malformed` and `truncated`, which is the only path that
parses the backup — a routine poll reads the in-memory accounting instead, so polling can never be a second source of
pressure on a saturated host.

Read it this way: `spilledToDeadLetter` above zero, or a non-empty `deadLetter`, is real loss. `timedOut` and
`lateRecorded` beside a live `queueDepth` are a slow connection pool that has not cost anything yet — the old
`[run-audit] timed out recording …` line called that shape a lost row and usually was wrong. `available: false` with
`buffered: true` means the writer has not been built (no durable backend yet, or nothing emitted), while
`buffered: false` is the `FUSION_RUN_AUDIT_BUFFERED=0` kill switch; the two flags exist so "switched off" and "nothing
queued" do not both read as zeroes. `pid` is present because every process owns its own writer — an engine, a
dashboard, a CLI, and a child worker each report their own numbers, and none of them is a cluster total.

The drain, the byte-capped JSONL backup outside the PostgreSQL failure domain, and the replay contract are documented
in [run-audit.md → The sink drain](run-audit.md#the-sink-drain-how-a-best-effort-row-is-queued-counted-and-spilled-rufu-453).

## Agent performance reflection telemetry

Agent reflection generation emits one run-audit event for every `AgentReflectionService.generateReflection` attempt, covering manual dashboard requests, executor/post-task tools, heartbeat tools, and self-improve callers from the shared service seam.

- Run-audit events (`database` domain, target `agentId`):
  - `reflection:generated` metadata: `{ agentId, trigger, taskId?, reflectionId, tasksCompleted?, tasksFailed?, avgDurationMs?, commonErrorCount, insightCount, suggestedImprovementCount }`.
  - `reflection:skipped` metadata: `{ agentId, trigger, taskId?, reason: "no-history" | "not-completed" }`.
  - `reflection:failed` metadata: `{ agentId, trigger, taskId?, errorClass }`.
- Trigger taxonomy is preserved from `ReflectionTrigger`: `manual`, `periodic`, `post-task`, and `user-requested`.
- The events use synthetic run context with phase `reflection` and source equal to the trigger so they correlate in the run-audit stream without requiring caller-specific wiring.
- Guardrail: reflection diagnostics persist IDs, counts, reasons, and error classes only; never prompt text, reflection summaries, insight strings, suggested-improvement text, or free-form trigger details.

### Post-task performance capture (`reflection:captured`, FN-7528)

`AgentReflectionService.captureTaskPerformance` is a deterministic, non-LLM counterpart to `generateReflection`: it runs once per completed task at the executor completion seam (`TaskExecutor.signalTaskComplete`), guarded by `reflectionService` presence, `settings.reflectionEnabled`, and an assigned agent id. It never calls the model provider and persists a compact structured `post-task` `ReflectionMetrics` record — duration, packages/files touched, verification command(s) + file-scoped-vs-broader classification, and retry/rework count — sourced only from the completed `Task` record. Fields whose source is unavailable are omitted, never fabricated.

- Run-audit event (`database` domain, target `agentId`):
  - `reflection:captured` metadata: `{ agentId, trigger: "post-task", taskId?, reflectionId, retryReworkCount?, filesTouchedCount?, packagesTouchedCount?, verificationFileScoped?, durationMs? }`.
  - Skipped/failed captures reuse the existing `reflection:skipped` (`reason: "no-history" | "not-completed"`) and `reflection:failed` (`errorClass`) event types above.
- Guardrail: capture telemetry stays ids/counts/outcomes-only — `verificationScopeReason` free-text, the deterministic one-line `summary`, and any prompt/reflection prose never reach run-audit metadata (they are stored only in the `ReflectionMetrics`/`AgentReflection` record itself).
- Capture is best-effort and fire-and-forget: a capture failure never blocks or fails task completion, and an in-memory per-taskId guard prevents duplicate captures across the executor's several completion call sites (fresh completion, duplicate in-review re-entry, auto-recovery, paused-after-completion finalize, retry-completed).

## Task-ID integrity measurement failures (`[task-id-integrity]`)

<!--
FNXC:TaskIdIntegrityCanary 2026-10-18-23:59 (RUFU-333):
Documented because the absence of this line used to be the misleading signal. The synchronous store-path
canary swallowed every read failure and logged a warning about degrading to a healthy report, so a broken
database produced a clean bill of health and no error line at all.

The store's task-ID integrity canary logs through `coreLog.error` whenever a measurement lands on a state worth announcing:

- `[task-id-integrity] measurement failed; canary is unmeasured, NOT healthy` — `{ error }` names the driver's reason. The measurement did not complete, so the canary publishes no verdict; the cached report is `status: "error"` and `taskIdStateReconciled` stays false.
- `[task-id-integrity] anomaly detected` — `{ anomalies }` lists what the completed scan found.

Both lines are deduped by a namespaced signature (`failure:<reason>` / `anomaly:<json>`) held per store instance, so a database handle that is permanently unusable — backend mode's synchronous handle is — cannot append the same line on every store open. The signature namespaces the two kinds, so a failure can never silence a later anomaly or the reverse. The cached state is rewritten on every attempt regardless of dedupe: log silence is a logging decision and never a claim about the corpus.

Operator interpretation: this line repeating across restarts means the canary has never seen your task tables, which is not the same fact as "the IDs are consistent". `GET /api/health` answers from the async PostgreSQL probe and is unaffected by the synchronous canary; the store-side state is what `taskIdStateReconciled` and the store's own report surface.

## Windows embedded PostgreSQL recovery (`[postgres-embedded]`, FN-8522)

When a Fusion-owned Windows embedded cluster reports the exact `0xC0000142` backend DLL-initialization failure followed by PostgreSQL's shutdown chain, the existing startup/System diagnostic sink records:

- `detected Windows DLL initialization shutdown; attempting one owned-cluster recovery`
- `Windows owned-cluster recovery completed; existing pools may reconnect`, or
- `Windows DLL initialization recovery failed after one retry; restart Fusion and inspect the System log`

The recovery budget is one per lifecycle and applies only to a post-readiness cluster Fusion started. It never restarts a joined cluster. On the terminal message, restart Fusion; if it repeats, retain the System log and bundled-runtime version for support rather than deleting the data directory.

## Process supervisor (`[process-supervisor]`)

The process supervisor logs when it registers a supervised child, starts teardown, expires the grace window, escalates to `SIGKILL`, or observes a natural child exit.

- `spawned pid=<pid> pgid=<pgid|n/a> command=<cmd>` — child registered for parent-death supervision.
- `terminating pid=<pid> pgid=<pgid|n/a> reason=<reason>` — teardown cascade started.
- `grace expired for pid=<pid>; escalating to SIGKILL` — child ignored the grace window.
- `sent SIGKILL to pid=<pid> pgid=<pgid|n/a>` — hard-kill escalation sent.
- `maxLifetime exceeded for pid=<pid> after <ms>ms` — lifetime watchdog fired.
- `child pid=<pid> exited naturally code=<n|null> signal=<n|null>` — child deregistered after exit.

## Stuck-session in-place recovery (`[executor]`, `[stuck-detector]`)

Time-based stuck detection floors activity timestamps using `settings.engineActiveSinceMs` plus `settings.engineActivationGraceMs` (default `300000`). The runtime stamps `engineActiveSinceMs` on startup and each unpause transition so engine pause/downtime does not count as quiet time.

A silent or repetitive session is disposed and the same task is re-dispatched after the old execution lock unwinds. Recovery preserves the current column, workflow node, current step, worktree, branch, and completed-step progress. Repeated silence remains automatically recoverable; no stuck-kill budget, terminal failure, decompose instruction, or human approval hold is emitted. User-paused tasks remain untouched.

## Idle heartbeat backoff (`idle-ladder`, `idle-backoff:<stepMs>`, RUFU-268)

An unassigned agent whose heartbeats keep acknowledging "nothing to do" is deliberately woken less often:
base → 2× → 4× → … up to `heartbeatIdleBackoffCapMs` (default 30 min), reset by the first run that finds
work. Two surfaces say which decision a tick got.

- `timer-heartbeat-idle-deferred agentId=<id> stepRemainingMs=<n>` (debug) — the board DID change, and this
  agent's own ladder chose to keep waiting. The distinguishing field is the wake-decision reason code:
  `idle-backoff:<stepMs>` means "new signal, waiting on the ladder", while `no-fresher-signal` is the older
  STAS-300 answer "nothing changed at all". A deferred tick still records its heartbeat and still stamps
  timer liveness; it just does not open a session.
- `idle-ladder advanced for <id>: streak N -> M step=<ms>` / `idle-ladder cleared for <id>: …` (debug) —
  the ladder transition itself, with its durable `agent:heartbeat-idle-ladder` row (see
  [`run-audit.md`](run-audit.md)).
- `idle-preflight-unavailable` / `idle-preflight-board-probe-failed` (debug) — the compact question could
  not be answered, so the tick fell through to the full heartbeat session. These are cost signals, never
  correctness failures: every fall-through path is the pre-RUFU-268 behaviour.

To answer "why has this agent not woken?", read its `runtimeConfig.heartbeatIdleStreak` and
`heartbeatLastNoWorkAt` against `heartbeatIntervalMs`: the rung it sits on is the wait the scheduler is
holding it to, and the dashboard's Unresponsive threshold and next-heartbeat countdowns stretch by that
same rung. An agent with no `heartbeatIdleStreak` is not idling at all and is timed exactly as before.

## Reports health stale-classifier diagnostics (`[reports-health]`)

Direct-report stale decisions in `HeartbeatMonitor.buildReportsHealthSection()` now emit a structured log when an agent is marked `**stale**`.

- Log shape: `[reports-health] stale report <agentId> intervalSource=<source> staleThresholdMs=<n> heartbeatAgeMs=<n>`
- `intervalSource` values:
  - `runtimeConfig` — interval came from cached per-agent runtime config
  - `persisted-agent` — cache was missing/sparse; interval came from persisted `getAgent()` row
  - `monitor-default` — no per-agent interval available; monitor default interval used
- `staleThresholdMs` is the computed stale threshold (`max(1.5 × interval, 5m floor)`). For an agent the
  idle-backoff ladder is holding (RUFU-268) the `interval` in that product is the agent's own current ladder
  step rather than its configured cadence, so the log line names the threshold the briefing actually used;
  an agent that is not idling resolves to its configured interval unchanged
- `heartbeatAgeMs` is the report's current heartbeat age at classification time
- Healthy reports do not emit this diagnostic; only stale decisions do

## Merge temp worktree cleanup classification (`[merger]`)

Fusion merge cleanup treats a narrow class of temporary merge/post-merge worktree removal failures as non-fatal only after Git admin state proves there is no registered worktree leak.

- Applies to Fusion-created temp merge paths such as `fusion-ai-merge-*` and post-merge paths such as `post-merge-*` during `merger-cleanup` / `merger-post-merge` removal.
- Trigger shape: `git worktree remove --force <path>` fails with validation text such as `fatal: validation failed, cannot remove working tree: '<path>/.git' is not a .git file`.
- Recovery proof: Fusion runs `git worktree prune`, then inspects `git worktree list --porcelain`.
- Harmless classification: if the target path is absent from porcelain after prune, the merger logs that cleanup remove failed but no registered worktree remains. If a directory still exists, Fusion reports it as residue for operator inspection; it does not delete arbitrary `/var/folders` content.
- Leak classification: if the target path is still present in porcelain after prune, the cleanup failure remains visible as a real registered-worktree leak.

Operator verification command:

```bash
git worktree list --porcelain | grep -F "<temp-worktree-path>"
```

No output means Git no longer registers that temp path; matching `worktree <temp-worktree-path>` output means the leak is still registered and needs operator cleanup.

## Temp-filesystem ENOSPC class: bytes-full vs inodes-exhausted (RUFU-397)

An `ENOSPC` failure says "no space left on device" and nothing else, but a filesystem runs out of space in two different ways: the byte pool can be full, or the **inode table** can be empty while most bytes are still free. tmpfs sizes its inode table at mount time, so the second shape is common on `/tmp` and is invisible to `df -h`. Both return the same errno (28), so every failure record reads as a full disk on a host that is not full, and the operator cannot reach the real remedy (release inodes, or move the lane off tmpfs).

Fusion now names the class in the failure record itself. One helper owns the classification — `classifyTempFs` / `annotateEnospcFailure` / `annotateEnospcError` / `tempFsClassSuffix` in `packages/core/src/temp-fs-diagnostics.ts` — and it **never throws**: an implausible, unreadable, or unsupported `statfs` result means "no opinion", and the original message passes through byte-for-byte. The probe runs only after text detection has already decided a failure is ENOSPC, so a normal failing test never pays for it, and at most once per recorded failure.

The class line is appended to the message text, so it reaches the operator through the record each lane already writes — no new lifecycle owner, no new park lane, no new audit reason:

| Lane | Record that carries the class |
|---|---|
| AI-merge clean-room creation | the merge park on the card, plus the engine merge-retry History line |
| `fn_run_verification` | the tool response `Failure summary:` block |
| Engine boot singleton guard | the `Engine start failed: …` runtime log line |
| Stale-tmpdir sweep | the `cleaned …` engine log line for each scratch directory it reaps |

The sweep is the **remedy**, not another annotated record: its `worktree:tempdir-sweep` audit row carries counts and fixed reasons only, never the class or a path, because the inode figures are a filesystem measurement and the sweep's own contract forbids putting paths in run-audit. Where the class is concerned, the sweep reduces how often the other three records have to be written at all.

Because a creation failure targets a path that by definition does not exist — the socket file was never bound, the scratch directory was never made — the probe reads the target and then its nearest existing ancestors, up to four levels, and stops at the filesystem root. The class line therefore names the path it actually measured (`on /var/folders/…`, not the phantom path that failed), and an unreadable chain yields no opinion rather than a guess.

Shape of the annotation (integers stay unseparated so a grep for them works):

```text
ENOSPC: no space left on device, mkdtemp '/tmp/fusion-ai-merge-fn-1-a1b2c3' [temp-fs class: inode-exhausted (ENOSPC) on /tmp — 0 of 1048576 inodes free, 52G bytes free (not a byte-full disk; release inodes or move the lane off tmpfs)]
```

Two deliberate consequences:

- **Engine boot stops claiming "already running" for a filesystem refusal.** `acquireEngineSingleton` folds any guard-creation error into `EngineAlreadyRunningError`, whose only consumer reads that class as positive proof another process owns the project and skips it silently — a clean startup log and no engine. A creation failure the probe can classify as errno 28 now throws `EngineStartupEnvironmentError`, so the project lands on the honest `Engine start failed:` warning. `EADDRINUSE`, the genuine already-bound case, keeps its existing error and message unchanged.
- **The class line repeats the `ENOSPC` token**, because the honest-blocked classifier matches that literal token and a prose-only sentence ("no space left on device") matched no host code before, which made a genuine host failure look AI-repairable. The guarantee the tests pin is asymmetric on purpose: annotating may never remove or reroute a classification, and may add one.

Fusion also reaps its own contribution to the problem. The stale-tmpdir sweep covers Fusion-created scratch prefixes under `os.tmpdir()` under a dedicated floor (`TEMP_SCRATCH_REAP_AGE_MS`, 24 h — an order of magnitude above the merge clean-room floor, because a scratch directory carries no task id and in-process session liveness cannot see another process's request, so age is the only available evidence). A prefix is admitted only when its creator's release path was verified to run on every leg, and the list records both the admitted prefixes and the ones deliberately excluded: process-lifetime artifacts (`fn-pkg-`, `fn-bunfs-<pid>`, `fn-experiment-*`, `fusion-worktree-sync-*`, `fusion-agent-export-*`, `fusion-test-workers-*`, and `fusion-engine-*.sock`, which is the singleton guard itself) and third-party temp content are never touched. The sweep is one non-recursive prefix-filtered directory read per root; it never runs `find` or `du` over the temp root.

Operator verification — read the two pools separately, because `df -h` alone cannot distinguish them:

```bash
df -h "$(node -e 'process.stdout.write(require("node:os").tmpdir())')"
df -i "$(node -e 'process.stdout.write(require("node:os").tmpdir())')"
```

`Use%` near 100 on the `-i` line with a healthy `-h` line is this class. `IFree` recovering after a sweep pass means Fusion reaped its own litter; if it does not, the remaining consumers are outside Fusion's admitted prefixes and only the operator can clear them.

### Redirecting TMPDIR for test lanes on an inode-starved host

While the inode table is exhausted, a test lane that calls `mkdtemp` cannot even produce its own fixtures — the suite dies in setup with errno 28 and looks like a product failure. Redirect the temp root to a filesystem that has inodes for the duration of the run:

```bash
mkdir -p .tmp-rufu397
TMPDIR="$PWD/.tmp-rufu397" <test command>
```

`os.tmpdir()` honours `TMPDIR`, so every Fusion helper that reads it — including the annotation probe and the sweep roots — follows the redirect with no code change, and the run stops depending on host `/tmp` state at all. Two cautions: delete the directory when the run ends and never stage it into a commit, because it holds test fixtures inside the repository; and note that a host genuinely out of inodes on its project filesystem too cannot be rescued this way — that is a real byte/filesystem problem, not this class.

## Hold-release slot attribution fields (RUFU-698)

The `slot` bucket was the sweep's only un-attributed giant (`slot=13770ms` inside a `30038ms` sweep with `released=0, held=3`), and the number that matters — cost per capacity reservation — could not be read from it because the reservation count was invisible. Two fields, printed **after** the reconciling parenthesis so the RUFU-209 bucket list keeps its exact meaning:

- `slot-calls=N` — reservations performed by this pass. `slot ÷ slot-calls` is now arithmetic on one line instead of an inference from `released`/`held` counters.
- `slot-detail=(slot:dispatch-guard=…, slot:scope=…, slot:claim-snapshot=…, slot:admission=…, slot:lease-write=…, slot:residual=…)` — the breakdown of the reservation leg, printed only when at least one child recorded time. Children are recorded as **full wall windows** and deliberately never enter the reconciling bucket list: a child that contained an inner sweep bucket (for example `unplanned`, which the planning guard records itself) would otherwise be subtracted twice, shrinking `slot` and inflating `unattributed`. `slot:residual` is the slot window minus every named child, so a cost nobody named is still visible as a number. `sum(slot-detail) <= slot` therefore holds whenever the slot window contains no inner sweep buckets, and `slot:residual` absorbs the difference when it does.

Reading it: a large `slot:claim-snapshot` means the reservation leg is re-deriving board-wide capacity state per candidate; a large `slot:admission` means the serialized admission drain itself dominates; a large `slot:residual` means unobserved work inside the reservation and is the cue to add a named child, not to raise the sweep budget.

## Hold-release truncation rotation field (RUFU-698)

- `rotated-deferred=N` — the sweep evaluated `N` cards first because the previous pass was budget-truncated before reaching them. Printed only when `N > 0`, and only on the full summary line: a pass truncated in its preamble never built an ordered candidate list, so it rotated nothing and printing the field there would be a claim about work it did not do.

Reading it: `rotated-deferred` recurring pass after pass means the board cannot be evaluated inside the budget at all, and the lever is the cost of the leg named by `slot-detail`, not `SWEEP_BUDGET_MS`. A pass that finishes inside its budget clears the rotation, so the field disappearing is the signal that the queue head is no longer being inverted.

## `/metrics` observability endpoint (RUFU-081)

The dashboard HTTP server exposes **`GET /metrics`** — a plain-text Prometheus exposition endpoint (`text/plain; version=0.0.4; charset=utf-8`) serving the system / runtime / Fusion-domain measurements that earlier CPU and UI-responsiveness diagnoses had to collect by hand (`curl /api/health` for event-loop latency, `ps` for child-process cadence, `psql` for query rate, RAM-usage sampling for RSS). A `curl /metrics` returns the same numbers a Prometheus/Grafana scrape would consume; no OTLP collector or `prom-client` dependency is involved — the module serializes Prometheus text in-process.

### Contract

- **Public, outside `/api`:** the route is mounted at the app level (before the SPA catch-all and `express.static`), so it returns Prometheus text rather than `index.html`. Daemon bearer-token auth only protects `/api/*`; `/metrics` is intentionally unauthenticated. The body carries **numeric values plus low-cardinality string label values** — no secrets, no prose, no request payloads, no run-audit telemetry. The label values do include registered **project identifiers** (`fusion_domain_project_running_agents{project="…"}`) and board column names, so any client that can reach the port can enumerate open project ids. Bind the port to a trusted network when that disclosure is not acceptable (CodeRabbit Major review fix 2026-08-18-11:53: the earlier "numeric gauges only" wording did not match the emitted body).
- **Non-blocking by construction:** the `/metrics` handler renders **synchronously** from pre-read snapshots. It performs zero awaited I/O — a scrape completes in O(metric count) work and can never itself starve the event loop or trigger an on-demand DB/ps query. All sampling happens on pre-read tick timers (see cadence below).
- **Run-audit blackline (FN-7158/FN-7528):** no metric content, relabeled names, timestamps, or numeric snapshots are written to the run-audit. The endpoint computes on scrape from in-process state; nothing here emits a documented run-audit event.

### Retention census and pressure signal (RUFU-257)

The retention families answer a question the earlier families structurally could not: an unbounded in-process cache grows for days while CPU stays flat and every endpoint keeps answering, so **nothing operational was abnormal** — the pre-RUFU-257 dashboard leak reached 10.77 GB of RSS with a perfectly healthy event loop. The census (`packages/dashboard/src/lib/retention-census.ts`) is the attribution layer: every bounded module-scope cache **registers** a source with a probe (entries, approximated bytes, expired entries) and a named ceiling.

- **A registered source always renders, at zero.** A missing line therefore means *not registered*, and `source_entries{source="…"} 0` means *empty*. This is the whole point of the attribution: "the number is zero" and "nobody ever looked at that cache" must stay distinguishable.
- **Coverage is a dominance signal, not a health percentage.** `coverage_ratio` is `trackedBytes / heapUsedBytes`, and it is never expected to approach 1: parsed IR, in-flight store rows, and off-heap `Buffer`/`Uint8Array` retention (visible in RSS, invisible to `heapUsed`) are all residual. Measured with 1 000 distinct client addresses plus 1 000 issued short-lived tokens against a ~337 MB harness heap: `tracked_bytes` 863 408 and `coverage_ratio` 0.002557 (≈183–211 B per IP window, 286 B per token). The two usable readings are **one source dominating `tracked_bytes`** → fix that cache, and **`coverage_ratio` near 0 while `heap_used_bytes` climbs** → the growth is outside the census, go to a heap snapshot. `docs/solutions/performance/dashboard-heap-growth-runbook.md` carries the full decision table and the operator soak procedure.
- **Scrapes stay synchronous.** The census reads a pre-read snapshot produced on the sampler's existing 5 s tick (`RETENTION_TICK_MS`); `/metrics` never runs a cache probe on demand, so a scrape can never be O(cache size). A source whose probe throws is counted in `probe_failures`, logged, and skipped rather than aborting the body.
- **Off-heap retention is reported, never estimated as V8 heap.** `terminal_output_buffers` deliberately reports queue bytes and session count outside the TTL vocabulary — terminal output is held in `Buffer`s that never become V8-backed, so the census names the bytes where they are actually held instead of pretending they are a cache.
- **Pressure is operator-visible without a Prometheus install.** When `heapUsed` crosses 75 % of the V8 ceiling (`DEFAULT_HEAP_PRESSURE_RATIO`), or a registered source sits at its own ceiling for 3 consecutive samples (`DEFAULT_CEILING_STREAK_THRESHOLD`, ≈15 s), the sampler emits a pressure signal with a fixed reason code — `heap-ratio` or `source-at-ceiling` — consumed by `packages/dashboard/src/retention-pressure-notice.ts`: a runtime-log warning beginning `retention pressure (<reason>):` that names the largest retained source, its tracked bytes, the streak or heap share that fired, and the coverage percentage; plus one Mailbox system notice per reason per UTC day. Both channels are rate-limited to at most one signal per 10 minutes while the condition persists (`DEFAULT_PRESSURE_COOLDOWN_MS`). There is deliberately **no** `fusion_retention_pressure` series: the signal has to reach an operator who has no scraper configured, and the metric side already carries what the signal was computed from (`source_entries` against `source_ceiling`, `source_expired_entries`, `coverage_ratio`). Mailbox delivery is **best-effort and idempotent**: the dashboard resolves the engine's message store lazily through the structural `engine.getMessageStore()` seam (it must not import `@fusion/engine`), skips when that seam is absent, dedupes on `retention-pressure:<reason>:<UTC day>`, and absorbs a throwing, rejecting, or absent sink — observability can never break the census tick, an HTTP request, or server startup. The heap ceiling is **not** raised as part of this: a bigger `--max-old-space-size` would only postpone the same death and would silently shift the meaning of this threshold.

### Sampling cadence and lifecycle

- The request-latency recorder is an Express middleware mounted before route handlers, so it measures the **live serving path** (including `GET /api/health`), not a synthetic probe.
- Process CPU/memory gauges update every ~5s; the git-subprocess gauge every ~15s; the PG rate and domain gauges every ~5s. All timers are `unref()`'d so a running sampler never keeps the process alive. The process and git arms invoke the same sampler, so they share ONE in-flight guard key: at the default 5s/15s cadence the arms coincide every 15 s and the coinciding tick skips the duplicate `ps` probe instead of double-probing (CodeRabbit Major review fix 2026-08-18-11:53).
- Sampler **start** is wired into the server's listen override and **stop** into the close handler (co-located with the OTLP exporter lifecycle), and runs in both headless and non-headless modes. Both start and stop are idempotent and never break server startup/shutdown; both calls are wrapped in try/catch (same pattern as the OTLP exporter) so a failure is logged and can never skip the remaining close handlers.
- **Spawn-count hook:** on start, `child_process.spawn`, `fork`, `execFile`, and `exec` are wrapped with an atomic counter that delegates to the original via `.apply`, so child spawning (including `superviseSpawn` / `runCommandAsync` / `execFileAsync`) is never broken. On stop the original functions are restored exactly. The hook is idempotent (starting twice never stacks a second wrap).

### Best-effort degradation

- **Git-subprocess gauge:** a single-level `ps -o comm= --ppid <pid>` scan every ~15s counts live `git` children of the serving process. It never recurses and never scans the whole process tree. When `ps` is unavailable (Windows, non-POSIX, missing procfs), the gauge degrades to `0` rather than throwing.
- **PG query-rate sampler:** reads cumulative `pg_stat_database` xact_commit/xact_rollback deltas PER DATABASE from the store's live async layer on the tick, normalized to a per-second rate. It is best-effort: on a privilege-fenced PG, transient pool error, or absent async layer it keeps the last-known rate (or `0` on the first invalid sample) rather than throwing or hammering the DB. A failed-probe gap invalidates the retained baseline — the first success after the gap re-baselines and keeps the last-known rate, so a stats reset landing inside the gap can never produce a cross-epoch rate — and a backward delta on ANY single database is treated as a stats reset even when the cross-database sum stays positive. The baseline is also marked stale on **stop**: after a dashboard stop/restart the first success re-baselines and keeps the last-known rate, so a stats reset during the stop gap can never emit a cross-epoch rate either (Greptile P1 review fix 2026-08-18-11:53). Embedded PostgreSQL reads may be operator-only depending on context.
- **Domain gauges** come only from already-open project stores via `countRunningAgentsInStore` / `listRegisteredProjectStores` / `store.listTasks({ slim: true })`. Empty/undefined/duplicate project and empty-column states produce well-formed `0`-valued or absent metric lines, never malformed output; the sampler never opens a store or starts an engine to answer a scrape.
- **Value safety:** non-finite or non-numeric values are coerced to `0` so a single bad sample cannot abort the whole body; invalid metric/label names are sanitized to the permitted Prometheus character set.

## LLM prompt-cache telemetry (RUFU-284)

Per-request LLM behaviour is measured, not inferred. Three event kinds share the existing
`usage_events` table (no migration, no new database):

| kind | category | one row per |
| --- | --- | --- |
| `token_usage` | `llm-usage` | LLM call, carrying `inputTokens`, `outputTokens`, `cachedTokens`, `cacheWriteTokens`, `cacheReadReported` |
| `prompt_head` | `llm-prompt` | LLM call, carrying the serialized system-prompt identity: sha256 `headHash`, `headBytes`, `staticBytes`/`dynamicBytes`, `divergenceStatus`, `firstDivergenceOffset` |
| `prompt_end` | `llm-prompt` | LLM call, pairing `requestId` to the head so a lane's real head+tail composition is countable |

The writer is `emitLlm*Meta` in `packages/core/src/telemetry/llm-prompt-telemetry.ts`, reached through
`TaskStore.emitUsageEvent`. The value-builder is pure (it only returns the meta object); a build error —
over-budget meta, malformed token shape — becomes a swallowed fail-soft and the row is simply not
written. **Telemetry can therefore be missing while the call ran normally**, which is the first thing to
rule out before concluding a lane is idle. The whole meta block fits the shared 4096-byte
`usage_events.meta` budget (`LLM_TELEMETRY_META_BUDGET_BYTES`), and the divergence locator is dropped
before the row is ever attempted rather than allowed to overflow the budget and take the usage counters
with it.

### A lane shows no record: which seam to suspect

Lanes do not inherit a record; each one is an explicit decision at a call site. When a lane is missing
from Command Center → Tokens → LLM telemetry, check the named owner:

- **executor** — `packages/engine/src/executor/persist-token-usage.ts`. A central executor session never
  passes through `accumulateSessionTokenUsage`; ~70 call sites land in this one delta seam. A `prompt_head`
  row additionally needs the lane's `promptTelemetry` record (passed where the session is built, e.g.
  `run-implementation.ts`) so the pi session factory in `packages/engine/src/pi.ts` can install the
  per-request patcher.
- **heartbeat** — `packages/engine/src/agent-heartbeat.ts`. A run that holds a task credits
  `task.tokenUsage` and emits from there; an idle `isNoTaskRun` heartbeat emits event-only, so a lane
  that shows rows only while agents are idle is behaving correctly.
- **workflow-step** — `packages/engine/src/execution/step-session-executor.ts`. Event-only by design:
  step spend deliberately does not credit `task.tokenUsage`, which is the third accounting source.
- **reviewer** — `packages/engine/src/execution/reviewer.ts`. Reviewer spend has no `task.tokenUsage`
  writer at all, so this event is its only row.
- **merger** — `packages/engine/src/merge/merger-ai.ts` via the same delta seam as the executor.
- **chat** — `packages/dashboard/src/chat.ts`, beside the existing `chat_token_usage` write, never
  through a second accumulation path.
- **triage / planner** — `packages/engine/src/triage.ts`.

A lane absent from the vocabulary but present in the engine (`custom` agents, ephemeral task workers) has
no row by construction: `lane` has no default and an absent lane means no row, never a mislabelled one.

### Reading the head columns

- `divergenceStatus: baseline` — the first head this process sent for the lane, so there is nothing to
  compare against. After a restart every lane reports `baseline` once; that is a restart, not a prompt
  change. `resetPromptHeadDivergenceLedger()` is the test/operator seam for that ledger.
- `identical` — same `headHash` as the previous request in the lane: a stable prefix, which is what
  RUFU-267/RUFU-268 (serialized-prompt byte stability) is supposed to produce.
- `diverged` + `firstDivergenceOffset` — the prefix moved, and the offset is the **character offset of the
  first difference against the previous head**, which localises the change: an offset near the end of
  `staticBytes` means something small moved at the tail of the stable half, while a small offset means the
  leading blocks changed and the provider cache for everything after it is cold.
- `diverged` + `firstDivergenceOffset: null` — the prefix moved but the previous head was not retained for
  comparison (oversized head, or a lane whose first observation was not retained). The divergence is real;
  only its position is unknown, and it is counted in `offsetUnknownCount` rather than being folded into a
  bucket.

`firstDivergenceOffset` is a *comparison against the previous request*, not a position inside a canonical
prompt, and it is computed in-process: two daemons observing the same lane each start from `baseline`.

### Query shape

The panel reads `GET /api/command-center/llm-telemetry?window=10m|1h` (read-only, project-scoped, unknown
window resolves to `1h`). The same aggregate is available directly for diagnosis, and the privacy
invariant is visible in the result: `meta` carries ids, numbers and fixed enums only.

```sql
select meta ->> 'lane'                      as lane,
       meta ->> 'requestId'                 as request_id,
       (meta ->> 'cachedTokens')::int       as cached_tokens,
       meta ->> 'headHash'                  as head_hash,
       meta ->> 'divergenceStatus'          as divergence
  from usage_events
 where kind in ('token_usage', 'prompt_head', 'prompt_end')
   and ts > now() - interval '1 hour'
 order by ts desc;
```

No new log namespace was added: this surface reports through its stored rows and the Command Center
section, never through `FUSION_DEBUG` lines, because a per-request log line is the thing that would leak
prompt content. Head text is never stored anywhere — hash, byte lengths and offsets only — so cache
behaviour stays measurable without the corpus being reconstructable.
